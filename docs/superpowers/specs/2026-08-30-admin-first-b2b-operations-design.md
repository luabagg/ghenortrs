# Admin-first B2B operations design

## Goal

Make `/admin` the sole day-to-day control surface for B2B operations: seller management, Bling connection and catalog sync, price-list imports, catalog access links, and operational history. Keep narrowly scoped public callbacks and email links only where an external system or recipient requires them.

## Scope and boundaries

- `/admin` remains private and is not described as a public page in `public/llms.txt`.
- Bling's OAuth callback remains public because Bling must redirect to it.
- Seller approval email links remain public, bearer-capability URLs, and do not require an admin login.
- The B2B catalog remains accessible only to approved sellers with a Supabase session. There is no B2B checkout.
- Existing `visible_b2b` values are preserved by product sync and price imports.
- No credentials, OAuth codes, Supabase action links, or raw signed tokens are included in UI responses, URLs generated by admin actions, or audit metadata.

## Authentication and authorization

### Admin roles

Replace the runtime `ADMIN_EMAILS` allowlist with an `admin_users` table keyed by the Supabase user ID. An administrator may manage other administrators from `/admin/configuracao`.

Bootstrap remains intentionally environmental but is one-time: `ADMIN_BOOTSTRAP_EMAILS` is consulted only while no `admin_users` record exists. A matching authenticated user visiting `/admin` becomes the first admin. Once one exists, the environment allowlist no longer grants access. This keeps deployment bootstrap possible without making configuration the daily authorization database.

`requireAdmin` checks the current Supabase user against `admin_users`; the bootstrap path is isolated in a dedicated server function and audited. All management actions use the existing server-side session/cookie authentication and never use a browser-supplied admin secret.

### Capability-specific secrets

Delete `B2B_ADMIN_APPROVE_SECRET`, `BLING_OAUTH_INVITE_STATE`, and all external secret-protected operational endpoints. Add `B2B_APPROVAL_LINK_SECRET`, used exclusively to sign seller-approval tokens.

Bling OAuth state is a random, short-lived nonce stored in an HttpOnly, Secure, SameSite=Lax cookie started by an authenticated admin. The callback requires exact cookie/state equality, clears the cookie on every result, and rejects callbacks without it. This binds OAuth to the initiating admin browser and makes the static invite-state bypass unnecessary.

## Seller approval and catalog access

### Registration approval email

Registration notification emails retain an `Aprovar cadastro` link. The GET route verifies but does not change state; it renders a concise confirmation page. A form POST carrying the same valid, unexpired signed token performs approval. This protects against email scanners and previews triggering an irreversible state change. The token carries the seller email, requested status, expiry, and a unique `jti`.

Create an `email_action_tokens` table holding a hash of `jti`, purpose, seller ID, expiry, consumed timestamp, and actor/result. The confirmation POST atomically consumes the token before applying the seller status, so it cannot be replayed. Approval actions are idempotent when the seller is already approved but never silently apply a non-approved status from a stale link.

### Send a seller catalog-access link

For an approved seller, the Sellers page provides `Enviar acesso ao catálogo`. It calls Supabase Auth's server-only `auth.admin.generateLink({ type: 'magiclink', email })` and emails the returned `action_link` through Resend. Supabase owns verification, one-time consumption, and configured magic-link expiration; the link redirects to the approved seller's normal B2B catalog route. The admin page reports delivery success/failure but never exposes the link for copying.

The action is unavailable for pending, rejected, or suspended sellers. The catalog API continues to check the seller database status after session creation, so an access link cannot bypass a later suspension. The operation is recorded in the audit log without the action link.

## Catalog operations

### Bling connection and sync

`/admin/produtos` gains an Operations panel using the current session-protected route action:

- Connection status based on the stored Bling token, with an expiry indicator.
- `Conectar/Reconectar Bling` starts the cookie-bound OAuth flow.
- `Sincronizar catálogo` calls `syncBlingProductsToCache` directly server-side.
- The result shows timestamp, number of products upserted, and a safe error message.

`/api/bling-oauth-start` and `/api/bling-sync` are removed. `/api/bling-oauth-callback` remains the only public Bling route and redirects to `/admin/produtos` with a short-lived result cookie/flash message rather than returning raw JSON.

### Tier price imports

Replace CSV upload with a paste form on `/admin/produtos`. The administrator selects Start, Pro, or Max, then pastes the price-list table copied directly from Bling/spreadsheet software. The supported input is tab-separated text (TSV), as produced by copying the supplied columns such as `Produto`, `Sku`, `GTIN/EAN`, `R$ Preço no Bling`, and `R$ Preço da lista`. The UI explicitly says to paste the original table rather than manually align whitespace: product names contain spaces, so whitespace-separated prose is deliberately not guessed.

The parser normalizes header accents/case and locates `Sku` plus `Preço da lista`; it ignores `Produto`, `GTIN/EAN`, and `Preço no Bling` for writes. It accepts Brazilian currency values such as `61,49` and `R$ 61,49`. It rejects missing required headers, rows without SKU, malformed list prices, conflicting duplicate SKUs, oversized input, and a paste without tabs. Exact duplicate SKUs with the same normalized price are collapsed and reported once.

Before any write, the route displays a preview: recognized input rows, matched SKUs and new values, unchanged values, missing SKUs, skipped/invalid rows, and duplicate resolution. The administrator must explicitly confirm that preview; the server retains a short-lived, integrity-protected preview payload so a submitted confirmation cannot be altered in the browser. The commit runs in a transaction.

The import updates only the selected tier's price column. It does not change Bling fields, seller tier selection, active status, or `visible_b2b`. It may update a cached inactive SKU, matching the former CLI behavior, and calls that out in the preview. Remove `scripts/bling-price-list-import.mjs`, `prices:import`, and their CSV instructions after this workflow is covered by tests and documentation.

### Product visibility

Preserve individual show/hide controls. Add a bulk selection action for the currently filtered product list with an explicit target state (show or hide), avoiding ambiguous toggle behavior. Every visibility mutation is audited.

## Audit trail

Create an append-only `admin_audit_events` table with event ID, actor admin ID/email, action, optional seller/product target IDs, safe JSON metadata, creation timestamp, and success/failure outcome. Record bootstrap, admin-role changes, seller status changes, approval-link consumption, seller access-link delivery, OAuth connect result, catalog sync result, price-import confirmation, and visibility changes.

Add an `/admin/atividade` read-only page showing newest events first. It must redact token material, OAuth codes, headers, and raw CSV content.

## Routes and user interface

- `/admin`: Sellers, approval/suspension controls, and `Enviar acesso ao catálogo` for approved sellers.
- `/admin/produtos`: product visibility plus Bling status/connect/sync and tier-price import.
- `/admin/atividade`: audit history.
- `/admin/configuracao`: administrators.
- `/admin/approve?token=…`: public confirmation page; POST consumes the approval token.
- `/api/bling-oauth-callback`: public callback only, cookie-bound then redirects to `/admin/produtos`.

Use existing `AdminChrome`, buttons, inputs, tables, surfaces, and dark technical tokens from `DESIGN.md`. Do not invent a dashboard visual language, new colors, or rounded component variants.

## Migration and deprecation

1. Ship schema, session authorization, and UI workflows.
2. Configure `B2B_APPROVAL_LINK_SECRET` and (only during initial bootstrap) `ADMIN_BOOTSTRAP_EMAILS`.
3. Remove `B2B_ADMIN_APPROVE_SECRET`, `BLING_OAUTH_INVITE_STATE`, `/api/bling-sync`, `/api/bling-oauth-start`, `catalog:sync`, and `prices:import` from production documentation and normal operations.
4. Keep `GET /api/admin-approve-seller?token=…` as a compatibility redirect to the confirmation page for one release; remove its secret-authenticated POST behavior immediately.
5. Update `docs/integrations/b2b-auth-bling.md`, `.env.example`, and relevant tests in the same change.

## Error handling and testing

- All admin actions require `requireAdmin`; non-admin sessions receive the existing login/forbidden flow.
- OAuth callback failures return to the admin product page with a generic message and log a redacted audit failure.
- Sync/import failures do not partially overwrite unrelated fields; confirmed imports are performed in a transaction.
- Email delivery failures do not claim successful delivery and are auditable.
- Tests cover permissions, token expiry/tampering/replay, GET-not-mutating approval, catalog-access eligibility, OAuth cookie/state validation, TSV header/currency parsing, missing and conflicting duplicate SKU handling, preview-integrity and commit behavior, field-preservation invariants, and audit redaction.
